# にほちゃんマイク：場の話題を記録・発信する機能

更新: 2026-10-23

## 目的と二つのモード

にほちゃんマイクは次の二つの独立した用途を持つ。

1. **記事録音**: 運営者が明示的に開始・停止し、音声から記事の下書きを作る。既存の NIHOapp の機能。
2. **場の話題**: 同意と説明がある場で運営者が開始し、今話していることを短く記録する。v2 以降は選んだ内容をにほちゃん bot が会員フィードへ投稿する。

記事録音の音声を場の話題へ、場の話題の音声を記事へ、本人の新たな操作なしに流用しない。v3 の同一機器では記事録音を優先し、その間は場の話題を一時停止する。

狙いは、現地にいない人が場の様子を知って訪れたくなることと、後からその日の学びを振り返れること。録音や文字起こしを公開すること自体は狙いではない。

## v1: Mac だけで試す

- macOS 26 以上の Apple Silicon Mac で動く、手動起動の CLI を最初の製品形にする。常駐サービス、ログイン時自動起動、定期タスクは作らない。MacBook でも同じ公開リポジトリを取得・ビルドできるようにする。
- 入力機器を運営者が指定する。録音開始時と各区切りで機器 UID を照合し、切断や既定入力の切替時は止める。Mac 内蔵マイクへ黙って切り替えない。
- v1 は入力マイクを待機中も監視し、周囲の音量を超える候補が続いた場合に短い音声だけをMac内Sound Analysisで確認する。発話として通ったら直前最大12秒のメモリ内音声を含めて録音する。確認用の一時音声は判定後すぐ削除し、中断時に残ったものは次回起動時に削除する。否定された候補は約10秒の間隔を置いて再確認する。録音は既定3分・最大5分ごと、または約30秒の静けさで区切って待機へ戻り、直前の区切りを次の録音と並行して処理する。待機中は長い音声ファイルを書かず、文字起こし・要約AIも起動しない。録音した区切りには再度Sound Analysisを適用し、見送りなら文字起こしを呼ばない。発話があることと内容を正しく聞き取れることは別なので、既定の `verified` はWhisperとApple SpeechTranscriberの文字起こしを照合し、食い違う区切りを見送る。明示指定で各エンジンを単独利用でき、比較実験用の Google Antigravity CLI の Gemini にも切り替えられる。Gemini 指定時のみ音声を Google 側へ渡す。Whisper のモデル取得と Gemini の利用は運営者の明示操作とし、クラウドへ自動で切り替えない。Google公式FAQは消費者向けプランでCLIを外部アプリに組み込む方法をサポートしないため、6時間運用の候補には含めない。現地MacBookで処理時間と精度、冒頭の取りこぼし、待機時のCPU使用率を確認する。
- 音声診断はまず音量を確認し、次にMac標準の分類器で3秒ずつ重複なく調べる。発話の分類確信度が0.25以上の時間を発話候補、0.50以上を発話、0.65以上を強い発話判定とする。発話候補が区切りの5%（最少3秒・最大8秒）に満たない場合、発話がその65%未満の場合、強い発話判定が2秒未満または発話候補の55%未満の場合は見送る。初期談笑区間は78/162秒でこの条件を満たさず、明瞭な講演区間は132/177秒で通過した。これは現地の実録音を用いて調整する初期値で、言葉の正確さを証明する閾値ではない。
- `verified` はWhisperとAppleを独立に文字起こしして照合する。照合を通過し、Whisperに文末がなくAppleに句点があり、3文字列のJaccard一致度が0.60以上の場合だけApple文を後段に渡す。一致度0.30〜0.60未満ならWhisper文を維持する。双方を文字・数字だけに正規化した3文字列のJaccard一致度0.30以上を暫定条件とし、短い結果、反復や定型幻覚を見送る。音声全体の一致は各語句の正しさを証明しないため、話題選択AIには20〜240文字の連続した根拠発言を抜き出させる。可能なら意味や具体例まで含む120〜240文字を選ぶ。軽微な表記差は元の文字起こしの近い箇所に戻し、途中で切れた節は次の行まで含める。現在の話者が本人の名乗り・紹介から分かる場合だけ、その箇所も別の原文として確認する。要約には確認した原文だけを渡し、話題名の地名を本文の主語へ自動で引き継がない。通常の要約は、短文の地名・人名・数値などが根拠に出るかコードで確認したうえで、主語・理由・否定・話者の言い換えを別のMac内AIにYES/NOで確認する。原文から定型文を組み立てる狭い例外では、列挙された語、直後の関係、話者の本人の名乗りをコードで確認する。根拠を超える主語や因果があれば同じ発言から一度書き直し、なお裏付けられなければ別の話題を一度だけ選び直す。それでも確認できなければ見送る。3区間での初期照合値は明瞭な講演0.63、談笑0.11、聞き取りにくい登壇0.14。現地評価で閾値と見送り率を調整する。
- 要約の既定は **Mac 内の AI**。Foundation Models を候補とし、実行前に利用可能性と日本語対応を確認する。投稿文だけは明示指定で、このMacのループバックにある Ollama の `qwen3.5:4b` または `qwen3.5:9b` を選べる。内部要約、話題選択、根拠確認、安全審査は Apple のMac内AIを使い続け、モデル未取得・停止時は録音前に失敗させる。クラウドへ自動で送らない。将来の Haiku API は別 adapter とし、明示設定した場合だけ使う。Claude Code のサブスク認証を継続運転する第三者アプリの認証として流用しない。
- 各区切りを「文字起こし → 内容が理解できる場合は140字以内の**内部要約** → 発信価値の判断・話題選択 → 採用時だけ80〜140字の投稿案 → 最終確認 → Mac 内ログへの記録」の順に処理する。内部要約は発信見送りでも短期間保持し、同じ録音セッションの次の区切りの話題理解に使う。内部要約だけが失敗し投稿文は採用できた場合、採用済み投稿文を次区間の内部メモに使う。別の録音開始・別ファイルの単発処理には自動で引き継がない。内部要約だけでは新しい投稿の根拠としない。元の文字起こしの該当箇所を確認し、今回の区切りに別の場所や話題が明示されたらそちらを優先する。同じセッションで15分以上発話が検知されない場合は会話文脈を失効させる。15分間投稿しなかっただけでは失効させない。
- 使用判定は、意味がわかり「今の状況を共有して行きたくなる」か「後で読んで役立つ知識」のどちらかに当たるかで決める。知識には豆知識、背景、成り立ち、理由、工夫、方法も含む。比較を優先せず、違いを選ぶ場合は何がどう違うかまで説明できる話題を選ぶ。条件を満たさない場合は投稿を「見送り」にするが、理解できた内容の内部要約は次の区切りに引き継ぐ。投稿本文は日本語80〜140文字（可視文字数）、1〜2文を目標にする。時刻は別フィールド。短文に具体性が足りない場合は根拠中の語を使って書き直すが、根拠確認を通った60〜79字の明瞭な案があれば字数合わせで壊さず採用候補に残す。明瞭な列挙と「重なりが話題を作る」という関係が原文の隣接箇所に明示されている場合だけ、原文の語を使う定型文も候補にできる。この定型文は話者の本人の名乗り、原文の語句、関係の順序をコードで検証し、通常の出力安全審査を通す。
- 話題選択の構造化生成は採否・話題名・原文引用の3項目に絞る。形式エラー時はラベル付きテキスト、次に原文引用だけの応答を試す。引用だけの応答は今回の文字起こしとの完全一致と原文の主語を確認し、話題名もその主語から取る。明示された見送りを形式エラーとして再試行しない。内部メモに具体的な学びがあれば、その主題に合う原文を優先する。引用末尾の私的・不明瞭な文は手前で切り、離れた原文をつながない。
- 教育と「学問を分け合う場」など、出典に対応する表現がある限定した一般語の言い換えは、漢字の完全一致だけで落とさず独立した意味審査へ渡す。名前・数値・話者・因果をこの例外で補わない。引用にある語でも、意味不明なASR語や意味を補えない口語は本文へ写さず、同じ話題の明瞭な役割・方法・条件から具体化する。引用の完結した最初の主張を伝聞にする抽出案も候補にできる。通常は意味審査に通し、単一の原文発言を一字も変えず括弧で示す候補だけはコードで原文一致・長さ・危険語を検証して意味審査に代える。出力安全審査は常に通す。安全審査の構造化生成が失敗した場合だけ、一語のYES/NOで再試行し、拒否・曖昧な返答・再失敗は見送る。
- 投稿生成と最大2回の書き直しは、選択済みの話題名を固定し、本文だけを `text` の1項目で構造化生成する。ParsingErrorなどの形式失敗時は本文だけのプレーン出力で一度再試行する。以前の「話題: / 本文:」2行形式も本文を取り出せるが、生成された話題名では選択済みの話題を変更しない。編集済み投稿指示の内容は保ち、出力形式だけを指定する。形式復旧は事実・伝聞・字数を自動補完せず、通常の根拠・意味・安全・長さ・文数・重複の各審査へ渡す。
- 同じ時間の予定情報は、v1 では任意のローカルテキストとして音声に添え、イベント名・予定上のゲスト・公開肩書の文脈に使う。予定は実際の話者や発言内容の証拠ではない。予定だけでゲストを現在話者にせず、固有名詞の表記を直す場合も音声の原文と出典を分けて確認する。v2 はNIHO Desktopが拠点と時刻で候補予定を取得し、運営者がイベントを確認して渡す。
- 知識や過去の発言は伝聞として扱える。「西御門の谷戸は縄文時代からなんだって」のように会話の内容をにほちゃんの言葉で伝えてよい。伝聞の文末は推奨するが採否の条件ではなく、どんな文末でも内容・根拠・安全性で判断する。今の場の様子は「今は谷戸の成り立ちについて話しているよ」のように現在形で伝える。歴史的事実の外部照合は必須にしない。ただし、話されていない細部や断定を足さず、話が不明瞭なら見送る。
- 人名、都道府県などの広い出身地、職業は会話に出ていれば本文や話題名に含めてよい。「松本さんは千葉出身のデザイナーなんだって」も共有可能な候補とする。個人的な会話が混じっても、共有できる話題があればMac内AIに選ばせる。連絡先、詳しい住所や現在の住まい、家庭、政治的主張、個人の信仰・宗教的勧誘、健康、個人の金銭事情、人間関係、未成年者の話などは出力しない。寺院の公開された歴史・文化・観光の取り組みや住職という肩書、不動産取引など一般的な話は扱える。候補の本文と話題名だけを別のMac内AI審査に通し、安全な話題を明確に切り出せないときに見送る。審査モデルが拒否・失敗したときも見送る。モデルへの指示に加え、出力の長さ・形式・危険語・重複をプログラムでも検査する。
- 同じ話題の継続は、直近の採用済み要約を比較して見送る。新しい視点や具体的な学びが増えた場合だけ次の記録を作る。出力には生成時刻と対象音声の終了時刻を持つ。
- 音声は作成から **72 時間**、生の文字起こしと要約候補の診断情報は **168 時間**保持し、期限が来たら自動削除する。研究段階で振り返るための期間であり、保存先は Mac 内のアプリ専用ディレクトリ（ディレクトリ 0700、ファイル 0600）とする。Git と GitHub Actions へ実音声を入れない。Gemini を明示選択した区切りだけは Google 側へ音声を送る。短文ログは研究結果として残し、明示削除できるようにする。
- Gemini 指定時の一時音声は専用の空の作業ディレクトリへ置き、CLI にはそのファイルだけを直接読ませる。別のツール呼び出しを要求した結果は採用せず、一時音声は終了時または次回起動時に削除する。Antigravity CLI 側の会話履歴・保持は Mac 内の削除契約とは別に扱う。
- 処理が落ちても保存済み区切りを重複生成しない。開始・停止・機器切断・モデル不足・空録音・変換失敗を区別して状態を示す。ログには本文、音声、文字起こしを混ぜない。

### v1 の操作と受入

- `doctor`: OS、SpeechTranscriber、日本語モデル、Mac 内 AI、入力機器、保存先を確認する。モデルの取得は別の明示操作にする。
- `inputs`: 入力機器の ID と表示名を列挙する。
- `run --input <ID>`: 指定した機器だけで録音を開始し、Ctrl-C で安全に止める。手動で録音中かが分かる表示を出す。v1 には停止・再開が確実にできることが必要。
- `audio-check --audio <file>`: 文字起こし前のMac内判定だけを表示する。発話候補秒数と見送り理由を現地音声で調整する。
- `once --audio <file> [--session <ID>]`: 同意を得た録音を 1 本処理し、現地 MacBook の最初の疎通に使う。既定ではファイルごとに会話を分離し、同一会話の連続ファイルとして試す場合だけ同じセッションIDを明示する。プライベートな成果物は同じ保存先へ置く。
- `review-audio --audio <file> --asr <engine>`: 同じ短い音声で文字起こし・使用判定・要約候補・最終チェックを再試行する。ログは変更しない。Apple / Whisper / Gemini の比較にも使う。
- `review-text --transcript-file <file>`: ローカルの文字起こしから使用判定・要約だけを再試行する。ログは変更しない。
- `inspect`: 保存済み文字起こし、内部要約と継続話題、使用判定と理由、投稿候補、最終確認、記録状態をローカル端末に表示する。旧版の候補は保存されていない場合がある。
- `monitor`: 録音元とは別の端末で、専用保存先の状態ファイルと処理済み区間を読み取り、録音状態・区切りまでの残り時間・処理段階・文字起こし・内部要約・採用判断と理由・投稿案・最終結果を更新表示する。読み取り専用で、Ctrl-C は表示だけを終了する。状態の更新が止まれば停止中と表示する。
- `internal-prompt`、`selection-prompt`、`prompt` と `preview --segment <ID> [--event-context-file <file>] [--internal-prompt-file <file>] [--selection-prompt-file <file>] [--prompt-file <file>]`: 内部要約、使用判定、投稿案の指示を表示し、保存済み文字起こしに編集した指示を試す。予定はログへ保存しないため、予定込みの再現時には同じファイルを再指定する。採用ログは変更しない。
- 合成音声と合成文字起こしだけを公開 CI で使う。現地の実会話はリポジトリと CI に入れない。

## v2: 会員フィードへの投稿

- v1 の安全な短文を投稿候補として NIHOapp へ渡す。最初は運営者の承認後にのみ、NIHO 鎌倉の**会員フィード**へ投稿する。投稿間隔は会話の区切りから独立し、同一話題や変化の少ない区切りは省略する。
- NIHO ログイン中の運営者の Desktop で開始・停止・ミュートをいつでも操作できるようにする。機器の入力状態と公開状態を別々に表示する。現地参加者へは施設案内時に録音目的を対面で説明する運用を前提とする。
- bot は個人のアクセストークンや機器トークンで既存の投稿 API を直接呼ばず、拠点・操作権限・公開範囲・重複キーを検証する専用の受け口を使う。最初は `SPOT_MEMBERS` 限定。自動投稿や一般公開は、承認運用での誤投稿率と現地の反応を評価した後の段階。
- 投稿は拠点のデータとして保存し、削除・訂正・通報・拠点 purge の既存契約に従う。音声や生文字起こしは投稿に添付しない。
- 来訪前の人に見せる目的には、会員フィードとは別に公開ページ向け候補の選定が必要。v2 の最初の公開範囲を会員に限定する判断とは区別する。

## v3: 実機の入力へ切替

- 記事録音と場の話題を機器上で区別し、同時録音しない。記事録音が始まると場の話題を一時停止し、終了後も運営者の操作なしに再開しない。
- 場の話題の音声入力を BLE マイクから実機 adapter へ切り替える。転送先と認証は別途設計する。既存の「記事録音→NIHO API」の経路をそのまま場の話題へ流用しない。
- 表示灯は録音・ミュート・接続不良を区別する。物理的な停止方法と、Desktop 側の停止・ミュートを一致させる。

## 評価の観点

現地で同意を得た複数回のセッションを使い、発話の取りこぼし、文字起こしの内容、話題の有用性、重複、個人情報やセンシティブな話題の誤採用、会話終了から短文までの時間、BLE 切断時の振る舞いを人が確認する。v2 の自動公開を許す基準はこの結果を見て定める。

## リポジトリ境界

この公開リポジトリには v1 の汎用コード、設計、合成 fixture だけを置く。実音声、生文字起こし、ローカル短文ログ、認証情報、施設の運用鍵は置かない。公開 CI は標準 GitHub-hosted runner のみを使い、実マイク、Apple の日本語モデル、本人の AI アカウントを要求しない。

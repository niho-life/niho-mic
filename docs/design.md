# にほちゃんマイク：場の話題を記録・発信する機能

更新: 2026-10-23

## 目的と二つのモード

にほちゃんマイクは次の二つの独立した用途を持つ。

1. **記事録音**: 運営者が明示的に開始・停止し、音声から記事の下書きを作る。既存の NIHOapp の機能。
2. **場の話題**: 同意と説明がある場で運営者が開始し、今話していることを短く記録する。v2 以降は選んだ内容をにほちゃん bot が会員フィードへ投稿する。

記事録音の音声を場の話題へ、場の話題の音声を記事へ、本人の新たな操作なしに流用しない。v3 の同一機器では記事録音を優先し、その間は場の話題を一時停止する。

狙いは、現地にいない人が場の様子を知って訪れたくなることと、後からその日の学びを振り返れること。録音や文字起こしを公開すること自体は狙いではない。

## v1: Mac だけで試す

- macOS 26 以上の Apple Silicon Mac で動く、手動起動の CLI を最初の製品形にする。常駐サービス、ログイン時自動起動、定期タスクは作らない。MacBook でも同じ公開リポジトリを取得・ビルドできるようにする。
- 入力機器を運営者が指定する。録音開始時と各区切りで機器 UID を照合し、切断や既定入力の切替時は止める。Mac 内蔵マイクへ黙って切り替えない。
- v1 は既定 3 分、最大 5 分の区切りで**連続録音**し、直前の区切りを次の録音と並行して処理する。録音と処理の間に1分の空白を置かない。Mac 内の Sound Analysis と固定閾値で無音・雑音・発話の少なさを診断し、見送りなら文字起こしを呼ばない。発話があることと内容を正しく聞き取れることは別なので、既定の `verified` はWhisperとApple SpeechTranscriberの文字起こしを照合し、食い違う区切りを見送る。明示指定で各エンジンを単独利用でき、比較実験用の Google Antigravity CLI の Gemini にも切り替えられる。Gemini 指定時のみ音声を Google 側へ渡す。Whisper のモデル取得と Gemini の利用は運営者の明示操作とし、クラウドへ自動で切り替えない。Google公式FAQは消費者向けプランでCLIを外部アプリに組み込む方法をサポートしないため、6時間運用の候補には含めない。現地MacBookで処理時間と精度を確認する。現地で発話検知・無音後停止を評価する。区切り間の会話を取り落とさないことを優先する。
- 音声診断はまず音量を確認し、次にMac標準の分類器で3秒ずつ重複なく調べる。発話の分類確信度が0.25以上の時間を発話候補、0.50以上を発話、0.65以上を強い発話判定とする。発話候補が区切りの5%（最少3秒・最大8秒）に満たない場合、発話がその65%未満の場合、強い発話判定が2秒未満または発話候補の55%未満の場合は見送る。初期談笑区間は78/162秒でこの条件を満たさず、明瞭な講演区間は132/177秒で通過した。これは現地の実録音を用いて調整する初期値で、言葉の正確さを証明する閾値ではない。
- `verified` はWhisperを主文字起こし、Appleを独立した照合用とする。双方を文字・数字だけに正規化した3文字列のJaccard一致度0.30以上を暫定条件とし、短い結果、反復や定型幻覚を見送る。音声全体の一致は各語句の正しさを証明しないため、話題選択AIには20〜240文字の連続した根拠発言を抜き出させる。軽微な表記差は元の文字起こしの近い箇所に戻し、途中で切れた節は次の行まで含める。要約にはこの原文だけを渡し、話題名の地名を本文の主語へ自動で引き継がない。短文の地名・人名・数値などが根拠に出るかコードで確認したうえで、主語・理由・否定などの言い換えを別のMac内AIにYES/NOで確認する。根拠を超える主語や因果があれば同じ発言から一度書き直し、なお裏付けられなければ別の話題を一度だけ選び直す。それでも確認できなければ見送る。3区間での初期照合値は明瞭な講演0.63、談笑0.11、聞き取りにくい登壇0.14。現地評価で閾値と見送り率を調整する。
- 要約の既定は **Mac 内の AI**。Foundation Models を候補とし、実行前に利用可能性と日本語対応を確認する。利用できなければ明示的に失敗し、クラウドへ自動で送らない。将来の Haiku API は別 adapter とし、明示設定した場合だけ使う。Claude Code のサブスク認証を継続運転する第三者アプリの認証として流用しない。
- 各区切りを「文字起こし → 使用判定・話題選択 → 80〜120字程度の要約候補 → 最終確認 → Mac 内ログへの記録」の順に処理する。使用判定は、意味がわかり「今の状況を共有して行きたくなる」か「後で読んで役立つ知識」のどちらかに当たるかで決める。知識には豆知識、背景、成り立ち、理由、工夫、方法も含む。比較を優先せず、違いを選ぶ場合は何がどう違うかまで説明できる話題を選ぶ。条件を満たさない場合は「見送り」にする。本文は日本語 140 文字以内（可視文字数）、1〜2文。時刻は別フィールド。
- 知識や過去の発言は伝聞として扱う。「西御門の谷戸は縄文時代からなんだって」のように会話の内容をにほちゃんの言葉で伝えてよい。今の場の様子は「今は谷戸の成り立ちについて話しているよ」のように現在形で伝える。歴史的事実の外部照合は必須にしない。ただし、話されていない細部や断定を足さず、話が不明瞭なら見送る。
- 人名、都道府県などの広い出身地、職業は会話に出ていれば本文や話題名に含めてよい。「松本さんは千葉出身のデザイナーなんだって」も共有可能な候補とする。個人的な会話が混じっても、共有できる話題があればMac内AIに選ばせる。連絡先、詳しい住所や現在の住まい、家庭、政治、宗教、健康、個人の金銭事情、人間関係、未成年者の話などは出力しない。不動産取引など一般的な話は扱える。候補の本文と話題名だけを別のMac内AI審査に通し、安全な話題を明確に切り出せないときに見送る。審査モデルが拒否・失敗したときも見送る。モデルへの指示に加え、出力の長さ・形式・危険語・重複をプログラムでも検査する。
- 同じ話題の継続は、直近の採用済み要約を比較して見送る。新しい視点や具体的な学びが増えた場合だけ次の記録を作る。出力には生成時刻と対象音声の終了時刻を持つ。
- 音声は作成から **72 時間**、生の文字起こしと要約候補の診断情報は **168 時間**保持し、期限が来たら自動削除する。研究段階で振り返るための期間であり、保存先は Mac 内のアプリ専用ディレクトリ（ディレクトリ 0700、ファイル 0600）とする。Git と GitHub Actions へ実音声を入れない。Gemini を明示選択した区切りだけは Google 側へ音声を送る。短文ログは研究結果として残し、明示削除できるようにする。
- Gemini 指定時の一時音声は専用の空の作業ディレクトリへ置き、CLI にはそのファイルだけを直接読ませる。別のツール呼び出しを要求した結果は採用せず、一時音声は終了時または次回起動時に削除する。Antigravity CLI 側の会話履歴・保持は Mac 内の削除契約とは別に扱う。
- 処理が落ちても保存済み区切りを重複生成しない。開始・停止・機器切断・モデル不足・空録音・変換失敗を区別して状態を示す。ログには本文、音声、文字起こしを混ぜない。

### v1 の操作と受入

- `doctor`: OS、SpeechTranscriber、日本語モデル、Mac 内 AI、入力機器、保存先を確認する。モデルの取得は別の明示操作にする。
- `inputs`: 入力機器の ID と表示名を列挙する。
- `run --input <ID>`: 指定した機器だけで録音を開始し、Ctrl-C で安全に止める。手動で録音中かが分かる表示を出す。v1 には停止・再開が確実にできることが必要。
- `audio-check --audio <file>`: 文字起こし前のMac内判定だけを表示する。発話候補秒数と見送り理由を現地音声で調整する。
- `once --audio <file>`: 同意を得た録音を 1 本処理し、現地 MacBook の最初の疎通に使う。プライベートな成果物は同じ保存先へ置く。
- `review-audio --audio <file> --asr <engine>`: 同じ短い音声で文字起こし・使用判定・要約候補・最終チェックを再試行する。ログは変更しない。Apple / Whisper / Gemini の比較にも使う。
- `inspect`: 保存済み文字起こし、使用判定と理由、要約候補、最終確認、記録状態をローカル端末に表示する。旧版の候補は保存されていない場合がある。
- `selection-prompt`、`prompt` と `preview --segment <ID> [--selection-prompt-file <file>] [--prompt-file <file>]`: 使用判定と要約の指示を表示し、保存済み文字起こしに編集した指示を試す。採用ログは変更しない。
- 合成音声と合成文字起こしだけを公開 CI で使う。現地の実会話はリポジトリと CI に入れない。

## v2: 会員フィードへの投稿

- v1 の安全な短文を投稿候補として NIHOapp へ渡す。最初は運営者の承認後にのみ、NIHO 鎌倉の**会員フィード**へ投稿する。投稿間隔は会話の区切りから独立し、同一話題や変化の少ない区切りは省略する。
- NIHO ログイン中の運営者の Desktop で開始・停止・ミュートをいつでも操作できるようにする。機器の入力状態と公開状態を別々に表示する。現地参加者へは施設案内時に録音目的を対面で説明する運用を前提とする。
- bot は個人のアクセストークンや機器トークンで既存の投稿 API を直接呼ばず、拠点・操作権限・公開範囲・重複キーを検証する専用の受け口を使う。最初は `SPOT_MEMBERS` 限定。自動投稿や一般公開は、承認運用での誤投稿率と現地の反応を評価した後の段階。
- 投稿は拠点のデータとして保存し、削除・訂正・通報・拠点 purge の既存契約に従う。音声や生文字起こしは投稿に添付しない。
- 来訪前の人に見せる目的には、会員フィードとは別に公開ページ向け候補の選定が必要。v2 の最初の公開範囲を会員に限定する判断とは区別する。

## v3: 実機の入力へ切替

- 記事録音と場の話題を機器上で区別し、同時録音しない。記事録音が始まると場の話題を一時停止し、終了後も運営者の操作なしに再開しない。
- 場の話題の音声入力を BLE マイクから実機 adapter へ切り替える。転送先と認証は別途設計する。既存の「記事録音→NIHO API」の経路をそのまま場の話題へ流用しない。
- 表示灯は録音・ミュート・接続不良を区別する。物理的な停止方法と、Desktop 側の停止・ミュートを一致させる。

## 評価の観点

現地で同意を得た複数回のセッションを使い、発話の取りこぼし、文字起こしの内容、話題の有用性、重複、個人情報やセンシティブな話題の誤採用、会話終了から短文までの時間、BLE 切断時の振る舞いを人が確認する。v2 の自動公開を許す基準はこの結果を見て定める。

## リポジトリ境界

この公開リポジトリには v1 の汎用コード、設計、合成 fixture だけを置く。実音声、生文字起こし、ローカル短文ログ、認証情報、施設の運用鍵は置かない。公開 CI は標準 GitHub-hosted runner のみを使い、実マイク、Apple の日本語モデル、本人の AI アカウントを要求しない。

# v1 話題抽出と短文の契約

更新: 2026-10-23

## 処理順

1. macOS の SpeechTranscriber で音声を文字起こしする。
2. Mac 内 AI が意味を読み取れるかを判定し、「今の状況がわかって行きたくなる共有」または「後で読むと役立つ知識」に当たる話題を一つ選ぶ。この段階では要約文を作らない。
3. 使用すると決めた話題だけ、別の Mac 内 AI で具体的な短文候補を作る。
4. プログラムで長さ・形式・センシティブ内容・重複を調べ、別の Mac 内 AI で候補本文と話題名の安全性を確認する。
5. 採用した短文を Mac 内のローカルログに記録する。v1 は NIHOapp へ投稿しない。

会話中の命令、URL、コードはすべてデータとして扱い、アプリの動作指示にはしない。使用判定と要約の指示は `selection-prompt` と `prompt` で表示でき、`preview` にファイルを渡せる。`preview` は保存済み文字起こしを再評価し、ログを変更しない。

## 言葉と採否

- 知識の要約は**その場で交わされた話の伝聞**。史実として保証しない。自然な「〜なんだって。」「〜と話していたよ。」などで結ぶ。場の様子は「今は〇〇について話しているよ。」のように現在形で伝えてよい。
- 聞こえた内容だけを使い、外部知識で補完しない。話されていない時代、数字、人物、地名、結論は足さない。
- 会話に出た人名、都道府県などの広い出身地、職業は出してよい。「松本さんは千葉出身のデザイナーなんだって。」は可。
- 連絡先、詳しい住所や現在の住まい、家庭、政治、宗教、健康、個人の金銭事情、人間関係、未成年者の話は出さない。一般的な不動産取引や仕事の進め方は扱える。訪問予定、入退室時刻、正確な人数も出さない。
- 音楽・環境音だけ、挨拶や相づちだけ、認識が崩れて意味を取れない区切りは見送る。
- 長さは利用者に見える文字数で140字以内、1〜2文。80〜120字を目安に、読んで内容が伝わるよう具体的に書く。条件に合わなければ見送る。
- 同じ話題が続き、新しい具体的な内容がなければ見送る。

## 診断と保存

通常処理の標準出力やエラーに生文字起こしは出さない。運営者が明示的に `inspect` または `preview` を呼んだ場合だけ、その端末へ「文字起こし → 使用判定と理由 → 要約候補 → 最終確認 → 記録状態」を表示する。音声は72時間、生文字起こしと候補の診断情報は168時間で削除する。公開リポジトリと CI に実会話を入れない。

## 例

| 会話の内容 | 結果 |
|---|---|
| 「西御門の谷戸には縄文時代から人がいたらしい。鎌倉時代の使われ方も面白い」と語る | `西御門の谷戸には縄文時代から人がいたらしく、鎌倉時代の使われ方も話題になったんだって。` |
| 庭の植物と日陰での育て方を語る | `庭の日陰で育てやすい植物と水やりの工夫について話していたんだって。` |
| リビングで谷戸の成り立ちを話している | `今は西御門の谷戸の成り立ちについて話しているよ。` |
| 「松本さんは千葉出身のデザイナー」と話す | `松本さんは千葉出身のデザイナーなんだって。` |
| 「来週、Aさんが病院へ行く」と話す | 見送り（個人・健康） |
| 政治への賛否を語る | 見送り（センシティブ） |
| 前の区切りから同じ庭の話が続き、新しい内容がない | 見送り（重複） |

## v2 の追加判定

v2 は候補をすべて投稿しない。投稿先の会員フィード、前回投稿からの時間、同一話題、運営者の承認、既存の公開範囲を判定する。v1 の `publish` は「ローカル短文として採用」であり、NIHOapp 上の公開許可を意味しない。
